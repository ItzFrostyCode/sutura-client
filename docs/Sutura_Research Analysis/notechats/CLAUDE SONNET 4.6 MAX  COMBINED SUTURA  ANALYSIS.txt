1.3 Business Reality Exists But Is WEAK in SUTURA

These are not missing from the thesis — they're in the approved scope. But the current implementation handles them poorly or incompletely.

A. The DP Gate Is Not Enforced
In real shops, no fabric is cut, no layout is started, and no order is moved to "In Production" until the deposit is received and verified. In SUTURA, a job order can move through status without a DP event attached. This is the single most important missing business logic.

B. Layout/Mockup Approval Workflow
Both tailoring shops (sublimation layouts) and fashion shops (sketch/peg approval) require explicit customer sign-off before production begins. Currently, SUTURA has no approval gate between "order created" and "production started." The customer must explicitly say "Approved" before the shop proceeds.

C. Appointment Types Are Collapsed
SUTURA treats all appointments as the same. In real business, there are at least 5 functionally different appointment types with different expected outcomes:


Initial Consultation (no order yet)
Measurement Taking (linked to a new job order)
First Fitting (linked to in-progress job order)
Final Fitting / Quality Check (linked to near-complete job order)
Pickup / Claiming (final handover event)


D. Rush Order Flag Is Missing
Real shops accept rush orders with a premium fee (30–50% markup). SUTURA has no rush designation. This forces shop owners to track rush jobs mentally or in a side notebook, defeating the system's purpose.

E. The "Suki" Notes Field Is Missing
The customer profile has standard fields but no free-text notes. In real business: "Client always rushes," "Prefers slim fit," "Corporate account — invoice required," "Family account — maintain measurements for 3 members." This is the most-used piece of institutional memory in a PH tailoring shop.

F. Branch Switcher Does Not Filter Data
The system audit explicitly flags this: "The selectedBranch state is not passed to any API calls in the layout. Pages don't currently filter by branch selection." A branch manager at Branch B should not see Branch A's job orders when they switch branches. This is a data isolation failure.

G. Alteration Jobs Have No Home
Short-cycle alteration orders (hemming, letting out seams, zipper replacement) are a high-volume, high-frequency service in real tailoring shops. They don't belong in the full Job Order flow (too heavyweight) but currently have nowhere to go in SUTURA.


1.4 SUTURA Has Features That Feel UNNATURAL in Real Business

A. CatalogOrder as a Separate Entity
In real PH shops, a "ready-to-wear" transaction is not meaningfully different from a custom order — it's just a custom order with no measurement phase and a shorter production stage. Having a completely separate CatalogOrder entity with its own controller, frontend route, and database table creates a parallel system that confuses both staff and the database schema.

Verdict: Eliminate CatalogOrder as a separate entity. Any "catalog item" becomes a job order with type: ready_to_wear and measurement_required: false. The catalog itself remains as a portfolio/showcase — not a shopping cart.

B. ServicePricing as a Fixed-Price System
In real PH tailoring shops, pricing is highly negotiable and context-dependent: "If the client buys 20 pieces instead of 5, the price per piece drops." "If they supply their own fabric, subtract ₱150." "If they want a rush delivery, add 30%." A fixed ServicePricing table is a fiction. No tailor quotes from a fixed menu.

Verdict: ServicePricing should display "starting from" prices only. Remove as a CRUD-heavy management module. Fold into Shop Settings as a simple "Services & Starting Prices" text configuration.

C. Support Ticket System as a Formal Module
Real PH shop owners do not open formal support tickets. They message on Facebook. The Support Ticket module is too formalized for the MSME audience SUTURA targets. It exists for the SaaS platform admin to receive complaints, but it shouldn't be a prominent sidebar item eating navigation real estate.

Verdict: Keep as a low-profile "Help" footer link. Not a Workroom module.

D. Specializations as a Standalone Nav Item
"Specializations" (barong, gown, suit, uniforms, etc.) is a tag set for the shop's identity — not something a shop owner manages on a daily or even weekly basis. It should be configured once inside Shop Settings and never touched again.

Verdict: Move to Shop Settings → Identity tab. Remove from sidebar navigation entirely.

E. Ready-to-Wear as a Separate Module
The frontend for Ready-to-Wear is a "minimal stub" by the system audit's own admission. The real-world volume of pure RTW transactions in bespoke tailoring shops is low. RTW is either: (a) liquidation of old stock, which is more fashion-shop behavior, or (b) a pre-made design that the customer wants made to their size, which is just a job order with a catalog reference.

Verdict: Eliminate Ready-to-Wear as a separate nav module. Fold into Job Orders with type: ready_to_wear.


1.5 Core Unified Business Model for SUTURA

SUTURA should model a service-based tailoring and alterations business with the following operational core:

SHOP DISCOVERY (Customer finds shop via map + specialization search)
    ↓
APPOINTMENT BOOKING (Customer books: consultation / measurement / fitting)
    ↓
JOB ORDER CREATION (Staff creates order after initial consultation)
    ↓
DEPOSIT GATE (Order locked until deposit is confirmed)
    ↓  [Optional: Layout/Mockup Approval]
PRODUCTION TRACKING (Staff updates stages: Cut → Sew/Alter → QC)
    ↓
FITTING APPOINTMENTS (Linked to job order, if applicable)
    ↓
COMPLETION GATE (Balance must be cleared before status → Complete)
    ↓
PICKUP / DELIVERY (Customer claims order, rates the shop)
    ↓
CUSTOMER RECORD UPDATE (Measurements saved, order archived)

This model covers: bespoke tailoring, alterations, RTW sales, and sublimation/custom uniforms — without requiring rental flow (which remains outside scope but can be added later as a service type).

5.1 The Duplication Problem

Currently SUTURA has three parallel order paths that share 80% of the same logic:


JobOrder → JobOrderStaff → Payment
CatalogOrder → Payment
Appointment (sometimes triggers an order, sometimes doesn't)


This creates: duplicate controllers, duplicate frontend routes, duplicate payment tracking, and conceptual confusion for users ("Is this a Job Order or a Catalog Order?").

5.2 Unified Order Architecture

One entity: JobOrder

With a type field that controls which stages and sub-fields are relevant:

Order TypeMeasurements RequiredFitting RequiredLayout ApprovalProduction Stagescustom_tailoring✅✅ (1-2 fittings)OptionalFull: Cut → Sew → QCalteration❌ (usually)✅ (1 fitting)❌Simplified: Alter → QCready_to_wear❌❌❌Minimal: Check Stock → QC

Catalog items become reference objects: catalog_item_id (nullable FK on JobOrder). Customer browses catalog → "I want this" → triggers an appointment booking (not a checkout).

Appointments remain as a separate entity but gain a job_order_id FK so fitting appointments are formally linked to the job they're for.

SECTION 7 — FINAL OUTPUTS


7.1 Final Unified SUTURA Business Model

SUTURA is a multi-tenant SaaS platform for tailoring and custom garment shops in Davao City that solves two problems simultaneously:

For Customers:
The map-based discovery portal lets them search for a tailoring shop by garment type and location, book an appointment directly, and then track their order from production through pickup — without a single phone call.

For Shop Owners:
A unified operations dashboard to manage job orders across their production pipeline, customer measurements, appointment schedules, staff assignments, and business analytics — replacing the notebook, the spreadsheet, and the Messenger chat window.

The Business Flow:

CUSTOMER discovers shop via map → Books appointment →
STAFF takes measurements → Creates job order → Customer pays DP →
Production proceeds through tracked stages →
CUSTOMER notified at key milestones (via SMS/notification) →
Fitting appointment scheduled if needed →
CUSTOMER pays balance → Picks up → Rates shop →
SHOP receives analytics: revenue, productivity, order velocity

The Platform Layer (Admin):
Shops must be verified before appearing on the marketplace. Subscription tiers control feature access and how many branches a shop can register. The admin monitors platform-wide activity and subscription health.

7.3 Final Role Architecture

SYSTEM ADMIN
─────────────────────────────────────────────────────
Portal: /admin
Owns: Platform data, subscription plans, shop registry
Sees: All shops (not their internal customer data), platform analytics
Controls: Shop approval/rejection, plan management
Does NOT see: Individual customer records, job order details

SHOP OWNER
─────────────────────────────────────────────────────
Portal: /dashboard (full)
Owns: Their shop(s) — all data across all branches
Sees: All orders, all customers, all staff, all analytics for their shop
Controls: All shop configuration, billing, branch management, staff accounts
Branch switcher: Can view any branch or all branches combined

BRANCH MANAGER
─────────────────────────────────────────────────────
Portal: /dashboard (scoped to their branch)
Owns: Their branch's data
Sees: All orders for their branch, all customers for their branch
Controls: Order management, customer management, appointment management
Does NOT see: Other branches' data, billing, branch creation, plan management
Branch switcher: Fixed to their branch

STAFF
─────────────────────────────────────────────────────
Portal: /staff-dashboard (simplified)
Owns: Their assigned job orders
Sees: Jobs assigned to them, customers they're serving, their appointments
Controls: Update production stage on assigned jobs, record measurements
Does NOT see: Financial reports, other staff's jobs (unless reassigned)

CUSTOMER
─────────────────────────────────────────────────────
Portal: /my-orders (authenticated, lightweight)
Owns: Their own profile, measurements, orders
Sees: Their job orders (status only), their appointments, their measurements
Controls: Book appointments (via public booking or portal), rate completed orders
Does NOT see: Other customers' data, shop internal notes, staff assignments


7.4 Final Order Flow Architecture

Across All Business Types — From Inquiry to Pickup

DISCOVERY (all types)
────────────────────────────────────────────────────────
Customer finds shop via map (specialization: barong / gown / uniforms / alterations)
→ Views public profile (services, hours, gallery, reviews)
→ Books appointment (type: consultation / measurement)

— or —

Customer walks in directly → Staff creates customer profile on the spot

INTAKE (type-specific)
────────────────────────────────────────────────────────
CUSTOM TAILORING:
  Appointment: Consultation / Measurement Taking
  Staff creates JobOrder (type: custom_tailoring, linked to appointment)
  Staff records body measurements → saved to CustomerProfile
  Due date calculated, total cost quoted, payment terms set

ALTERATION:
  Walk-in or appointment (type: consultation)
  Staff creates JobOrder (type: alteration)
  Garment inspected; alteration scope defined
  No measurements usually needed (alterations are on existing garment)

READY-TO-WEAR:
  Customer selects from catalog portfolio (in-store or via public profile)
  Staff creates JobOrder (type: ready_to_wear, catalog_item_id: linked)
  Size confirmed (no custom measurements needed)

DEPOSIT GATE (all types)
────────────────────────────────────────────────────────
Job order status: PENDING DEPOSIT
Staff logs deposit payment: amount / method (Cash / GCash / Bank) / reference number
Status unlocks → advances to next stage
[Order cannot move forward until deposit is confirmed]

LAYOUT APPROVAL (optional — for design-heavy orders)
────────────────────────────────────────────────────────
If layout_approval_required: true
  Staff sends digital proof to customer (via external channel: Messenger/WhatsApp)
  Staff logs: layout_approved_at timestamp, approved_by: "Customer (verbal / screenshot)"
  Status advances to production

PRODUCTION (stage tracking)
────────────────────────────────────────────────────────
CUSTOM TAILORING stages:
  → CUTTING
  → SEWING / ASSEMBLY
  → DETAIL / EMBROIDERY  (optional)
  → QUALITY CHECK  [trigger: notify customer "For Fitting" if fitting required]

ALTERATION stages:
  → ALTERATION IN PROGRESS
  → QUALITY CHECK  [trigger: notify customer "For Fitting" or "For Pickup"]

READY-TO-WEAR stages:
  → PREPARING
  → QUALITY CHECK  [trigger: notify customer "For Pickup"]

FITTING (if applicable)
────────────────────────────────────────────────────────
Appointment created (type: first_fitting, linked to job_order_id)
Staff records outcome: Approved / Needs Alterations
If Needs Alterations → return to production (brief loop)
If Approved → status advances to FOR PICKUP

COMPLETION GATE
────────────────────────────────────────────────────────
Job order status: FOR PICKUP
[Customer receives automated notification: "Your order is ready for pickup."]
Customer arrives → Staff verifies balance is paid (logs balance_paid_at)
If balance unpaid → cannot mark as COMPLETED (gate enforced)
Staff confirms handover → status: COMPLETED
Customer rates the order (1–5 stars + review text)

POST-ORDER
────────────────────────────────────────────────────────
Measurement record permanently linked to this job order
Order archived in CustomerProfile history
Revenue event logged to analytics


7.5 Final Shop Owner UX Architecture

Design Principles:


Surface what needs action. The home screen is not a dashboard — it's a triage board.
Operations over configuration. Settings are a one-time activity. Orders are a daily activity. Design reflects this frequency.
One flow, not parallel flows. All order types live in one Orders module. No split brains.
The order is the center of gravity. Everything — payments, fittings, staff assignments — orbits the job order.
Don't make the owner navigate to find out what happened. Status changes, payment events, and stage updates send notifications AND surface on the Today view.
Reduce confirmation friction. Common actions (log deposit, advance stage, create appointment from order) should be one-click from the order card — not a navigation journey.


Interaction Patterns:


Order cards show: customer name, garment type, current stage, due date, payment status. No need to click in for this info.
Stage advancement: inline button on order detail. Not a separate edit flow.
Quick deposit log: a "+ Log Payment" button directly on order card when status = PENDING DEPOSIT.
Appointment creation from order: "Schedule Fitting" button visible when order status = QUALITY CHECK.
Rush orders: visually tagged (⚡) throughout, sorted to top of lists by default.


Navigation Anti-patterns to Avoid:


Never require more than 3 clicks to update a stage on a job order.
Never require more than 2 clicks to find a customer's measurements.
Never require the owner to visit two separate modules to complete one workflow (e.g., visiting both "Jobs" and "Payments" to close out an order).



7.6 Final Thesis-Safe Version of SUTURA

The strongest capstone-aligned implementation:

Admin Portal (Build This)
A minimal /admin frontend currently missing from the system. Without it, the thesis objective "system administrator will review and approve tailoring shop verification requests" is unimplementable from a UI perspective. Build it as a simple 4-tab admin portal: Shops (pending queue + active list), Plans (CRUD), Analytics (platform metrics), Support.

Customer Portal (Build This)
The /my-orders lightweight customer portal — order status, upcoming appointments, stored measurements, rate-and-review. This is the most defensible thesis gap because the thesis explicitly states: "customers monitor their ongoing garment fulfillment status in real time." Real-time status requires a logged-in view, not just an SMS.

Job Orders (Expand This)
Add order_type, is_rush, deposit_gate, and production stages. This is the thesis core — make it bulletproof.

Appointments (Expand This)
Add appointment_type and linked_job_order_id. These two fields make the appointment module actually useful and tie it correctly to the order lifecycle.

Shop Discovery (Expand This)
The public map and search is the customer-facing showcase. Invest in the filter UX: by garment type, by location/distance, by operating hours, by specialization. This is what makes the demo impressive and the thesis defensible.

Branch Switcher (Fix This)
Pass selectedBranch to all API calls. This is a critical bug that breaks multi-branch use cases and undermines the entire branch management thesis objective.

Simplify These:


Merge Services into Shop Settings
Move Specializations into Shop Settings
Remove CatalogOrder entity; fold into JobOrder with type field
Remove Ready-to-Wear nav item
Remove Payments Queue nav item; payment events live inside orders
Remove Inventory folder permanently (empty, out of scope)


Defer These:


Rental lifecycle (add post-thesis as a job order service type)
Event bundling (post-thesis)
Layout file upload and customer approval workflow (post-thesis — the approval gate as a manual timestamp is within scope now)
Bulk team order matrix (post-thesis)
