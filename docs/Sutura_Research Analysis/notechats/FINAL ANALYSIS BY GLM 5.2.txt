## PHASE 1 — DATABASE AUDIT

### 1.1 Missing Tables

| # | Missing Table | Severity | Justification |
|---|---|---|---|
| 1 | `branch` | 🔴 Critical | Thesis explicitly includes branch management but no BRANCH table exists in the schema. SHOP table cannot represent multiple physical locations. |
| 2 | `notification_log` | 🔴 Critical | Thesis promises "automated SMS or email notifications at each stage transition" but there is no table to log notification delivery, status, or content. |
| 3 | `job_order_stage_log` | 🔴 Critical | Production stages (Cutting → Sewing → QC) are stored as a single ENUM field on JOB_ORDER. There is no history table tracking when each stage started, who updated it, and when it was completed. This makes the "real-time order progress monitoring" objective undefendable. |
| 4 | `measurement_version` | 🔴 Critical | Thesis claims "version-controls anatomical dimensions" but MEASUREMENT table has only `updated_at`. There is no version number, no previous-value retention, and no link to which job order triggered each measurement update. |
| 5 | `payment_timeline` (or split PAYMENT) | 🔴 Critical | PAYMENT table currently mixes subscription fees and customer order payments via nullable FKs on both `order_id` and `subscription_id`. Deposits (50% DP) and balances are not structurally separated. Real shops need "DP Collected" vs "Balance Due" as distinct financial events. |
| 6 | `appointment_type` (lookup) | 🟠 High | Thesis mentions "purpose" as free-text VARCHAR on APPOINTMENT. Without an enum or lookup table for appointment types (consultation, measurement, first_fitting, final_fitting, pickup), the system cannot enforce business rules like "a fitting appointment requires a linked job order." |
| 7 | `job_order_staff` (junction) | 🟠 High | JOB_ORDER has a single `staff_id` FK. In reality, multiple staff work on one order (cutter, sewer, embroiderer, QC). A many-to-many junction table with role and assignment date is needed. |
| 8 | `customer_note` | 🟠 High | The "suki card" institutional memory ("Client always rushes," "Prefers slim fit") is the most-used CRM feature in real PH shops. CUSTOMER_PROFILE has no notes field. |
| 9 | `catalog_item` | 🟠 High | The thesis mentions a "service catalog" but SERVICE table only stores service_name, base_price, garment_type. There is no table for portfolio/showcase items with images, descriptions, and categorization. |
| 10 | `role_permission` / `permission` | 🟠 High | RBAC is mentioned but no permission table exists. The USER table has a `role` VARCHAR/ENUM but there is no granular permission mapping. |
| 11 | `staff_specialization` (junction or lookup) | 🟡 Medium | TAILORING_STAFF_PROFILE has no specialization field. Real shops need to know which tailor handles barong vs uniforms vs gowns. |
| 12 | `shop_review` (separate from FEEDBACK) | 🟡 Medium | FEEDBACK is linked to JOB_ORDER (order-level review). Public marketplace reviews should be shop-level, not just order-level. |
| 13 | `audit_log` detail expansion | 🟡 Medium | AUDIT_LOG exists but lacks `entity_type`, `entity_id`, `old_value`, `new_value` columns. It only records action_type and description text. |
| 14 | `system_setting` / `shop_setting` | 🟡 Medium | No table for storing shop-level configuration (operating hours, booking policies, custom questions, landmark field). |
| 15 | `deposit` (liability ledger) | 🟠 High | Real shops track refundable deposits (rentals) separately from earned revenue. Mixing these in PAYMENT creates accounting confusion. |

### 1.2 Duplicate / Redundant Tables

| # | Issue | Severity | Detail |
|---|---|---|---|
| 16 | `SERVICE` vs `CATALOG_ITEM` concept overlap | 🟠 High | SERVICE stores service_name, base_price, garment_type. If catalog items are added, they will overlap with services. Need clear separation: SERVICE = capability declaration, CATALOG_ITEM = portfolio showcase piece. |
| 17 | `ORDER_MATERIAL` without `MATERIAL` reference | 🟡 Medium | ORDER_MATERIAL has `order_id` and `quantity_used` but no `material_id` FK. Since thesis excludes inventory, this table is orphaned — it tracks quantities of nothing. Either remove it or add a text field for material description. |
| 18 | `FEEDBACK` vs shop-level reviews | 🟡 Medium | FEEDBACK is tied to order_id only. If a customer wants to review the shop generally (not a specific order), there is no mechanism. |

### 1.3 Wrong Relationships

| # | Issue | Severity | Detail |
|---|---|---|---|
| 19 | `JOB_ORDER.staff_id` is single FK | 🔴 Critical | Only one staff member can be assigned. Real production involves cutter → sewer → embroiderer → QC inspector. Need junction table `job_order_staff` with `role` and `assigned_at`. |
| 20 | `APPOINTMENT` has no `job_order_id` FK | 🔴 Critical | Fitting appointments are not linked to the job order they belong to. Staff cannot answer "which order is this fitting for?" without manual cross-referencing. |
| 21 | `MEASUREMENT` has no `job_order_id` FK | 🟠 High | Measurements are linked to customer and shop but not to the specific job order that triggered them. Cannot trace "which order required this measurement update?" |
| 22 | `PAYMENT` dual nullable FKs (`order_id` + `subscription_id`) | 🟠 High | A payment record can reference either an order or a subscription. This creates ambiguity in queries and reporting. Should be split into `order_payment` and `subscription_payment` tables, or use a polymorphic approach with a `payable_type` field. |
| 23 | `JOB_ORDER.measurement_id` is NOT NULL | 🟡 Medium | Alterations and ready-to-wear orders do not require measurements. This NOT NULL constraint makes it impossible to create an alteration or RTW order without a measurement record. Should be NULLABLE. |
| 24 | `FEEDBACK` has no `shop_id` FK | 🟡 Medium | To display reviews on the public shop profile, the system must join FEEDBACK → JOB_ORDER → SHOP. Adding `shop_id` directly to FEEDBACK would simplify this query. |

### 1.4 Wrong Normalization

| # | Issue | Severity | Detail |
|---|---|---|---|
| 25 | `SHOP.coordinates` as VARCHAR/POINT | 🟡 Medium | Storing coordinates as a single VARCHAR field prevents spatial queries. Should use proper GIS POINT type or separate `latitude` and `longitude` DECIMAL columns. |
| 26 | `MEASUREMENT.measurement_data` as JSON/TEXT | 🟡 Medium | While JSON is flexible, it prevents querying individual measurement fields (e.g., "find all customers with chest > 40"). For a capstone, this is acceptable, but a `measurement_detail` child table with `field_name` and `field_value` would be more normalized. |
| 27 | `USER.role` as single ENUM | 🟠 High | A user can only have one role. In real shops, the shop owner is also the tailor and the cashier. Need a `user_role` junction table for multi-role assignment. |
| 28 | `SUBSCRIPTION_PLAN` has no feature list | 🟡 Medium | Plan tiers (Basic, Pro, Premium) need to define what features each tier includes (max branches, max staff, etc.). This should be in a `plan_feature` child table. |

### 1.5 Missing History / Audit / Logs

| # | Issue | Severity | Detail |
|---|---|---|---|
| 29 | No `deleted_at` soft-delete columns | 🟠 High | Hard deletes on CUSTOMER_PROFILE, JOB_ORDER, or PAYMENT would lose financial records. Every business-critical table needs `deleted_at TIMESTAMP NULL` for soft deletion. |
| 30 | No `updated_at` on most tables | 🟠 High | Only MEASUREMENT has `updated_at`. SHOP, SERVICE, SUBSCRIPTION_PLAN, CUSTOMER_PROFILE, TAILORING_STAFF_PROFILE all lack `updated_at`. Cannot track when records were last modified. |
| 31 | No `created_by` / `updated_by` columns | 🟡 Medium | Cannot determine which user created or modified a record. Important for accountability in multi-user systems. |
| 32 | No stage transition history | 🔴 Critical | JOB_ORDER.status is a single field that gets overwritten. There is no record of when the status changed, who changed it, or what the previous status was. |
| 33 | No payment status change history | 🟠 High | PAYMENT.status changes from Pending → Completed, but there is no log of when this happened or who verified it. |

## PHASE 2 — BUSINESS LOGIC AUDIT

### 2.1 Customer Journey Analysis

**Documented Flow (from thesis BPMN):**
```
Customer Search → Select Shop → Book Appointment → Staff Creates Job Order →
Measurement → Payment → Production → Fitting → Balance Payment → Pickup → Rate
```

**Issues Found:**

| # | Gap / Shortcut / Impossible Workflow | Severity | Detail |
|---|---|---|---|
| 51 | **No DP Gate Enforcement** | 🔴 Critical | The thesis BPMN shows "Process Payment" before "Generate Job Order Profile," but the database schema allows JOB_ORDER.status to advance without any payment record. There is no system-enforced rule preventing production start before deposit is verified. |
| 52 | **No Layout/Mockup Approval Gate** | 🔴 Critical | The BPMN jumps from "Approve Order" directly to "Allocate Materials and Labor." In reality, sublimation shops require explicit layout approval, and gown shops require sketch/peg approval. This step is entirely absent. |
| 53 | **No Alteration/Rework Loop** | 🔴 Critical | The BPMN shows "Perform Garment Alterations" after fitting, but there is no mechanism to revert JOB_ORDER.status from "Ready for Fitting" back to "Sewing." Once an order reaches QC, it cannot re-enter production. |
| 54 | **No Completion Gate (Balance Check)** | 🔴 Critical | The thesis states "No balance, no claim" is standard practice, but the schema allows JOB_ORDER.status to be set to "Completed" (or "Picked Up") without verifying that `balance_paid_at` is populated. |
| 55 | **No Inquiry/Quotation State** | 🟠 High | The customer journey starts at "Search" and jumps to "Book Appointment." In reality, there is a Messenger inquiry phase where the customer asks "Is this available?" and receives a verbal quotation. This pre-appointment state is missing. |
| 56 | **No Rush Order Workflow** | 🟠 High | Rush orders need priority queueing, premium fee calculation, and staff notification. None of this exists. |
| 57 | **Appointment-to-Order Conversion is Manual** | 🟠 High | The thesis says "tailoring staff can create job orders directly from scheduled fittings" but the BPMN shows this as a manual step. There is no "Convert Appointment to Job Order" button or automated linkage. |
| 58 | **No Customer Self-Service Tracking** | 🔴 Critical | Thesis explicitly states "customers monitor their ongoing garment fulfillment status in real time." But there is no customer portal. Customers receive SMS but cannot log in to see their order status. |
| 59 | **No Fitting Outcome Recording** | 🟠 High | When a customer attends a fitting, the system has no way to record: "Fitting passed" vs "Needs alterations" vs "Customer no-show." The appointment just becomes "Completed." |
| 60 | **No Pickup Verification** | 🟠 High | When a customer picks up an order, there is no system step to verify: (a) balance is paid, (b) customer identity, (c) physical handover confirmation. |
| 61 | **No Re-scheduling Logic** | 🟡 Medium | The appointment BPMN mentions "Request Reschedule" but there is no logic to prevent double-booking or to auto-suggest alternative slots. |
| 62 | **No Cancellation Logic** | 🟡 Medium | If a customer cancels after paying DP, what happens to the payment? The system has no refund workflow. |
| 63 | **No Multi-Branch Order Routing** | 🟠 High | In the main-satellite model, an order taken at Branch B may need to be produced at Branch A (where the machinery is). The system has no concept of order routing between branches. |
| 64 | **No Corporate/B2B Account Handling** | 🟡 Medium | Real shops service schools and corporations with PO-based billing (50% DP, 50% on delivery, 30-day terms). The system treats all customers as individuals. |
| 65 | **No Appointment Availability Checking** | 🟡 Medium | The BPMN mentions "Check Availability" but the schema has no staff availability or shop capacity table. Cannot prevent overbooking. |

### 2.2 Impossible Workflows Detected

| # | Issue | Severity | Detail |
|---|---|---|---|
| 66 | Creating an alteration order without measurements | 🔴 Critical | `JOB_ORDER.measurement_id` is NOT NULL. Alteration orders do not require new measurements. The schema makes this impossible. |
| 67 | Assigning multiple staff to one order | 🔴 Critical | `JOB_ORDER.staff_id` is a single FK. Cannot assign a cutter, sewer, and QC inspector to the same order. |
| 68 | Tracking which staff updated which production stage | 🔴 Critical | No `job_order_stage_log` table exists. Cannot answer "Who moved this order to Sewing and when?" |
| 69 | Viewing a customer's measurement history across versions | 🟠 High | MEASUREMENT table overwrites `measurement_data` on update. Previous measurements are lost. |
| 70 | Filtering appointments by type | 🟠 High | `APPOINTMENT.purpose` is free-text VARCHAR. Cannot filter "show me all first_fitting appointments this week." |
| 71 | Branch manager seeing only their branch data | 🔴 Critical | No `branch_id` on any table. Branch switcher in the UI does not pass to API calls. A branch manager sees all branches' data. |
| 72 | Customer rating a shop without a completed order | 🟡 Medium | FEEDBACK requires `order_id`. A customer cannot leave a general shop review. |

## What Makes SUTURA Feel Like a Real-World ERP Instead of a Student Project

> A student project has CRUD tables. An ERP has **enforced business gates**, **audit trails**, **operational dashboards**, and **role-scoped data isolation**.
>
> The single biggest transformation: **turning the dashboard from a reporting tool into a triage board.** When the shop owner logs in and the first thing they see is "3 deposits to verify, 2 orders overdue, 1 fitting at QC" — that's an ERP. When they see "Total Earnings: ₱45,000" — that's a student project.
>
> The second biggest transformation: **the order is the center of gravity.** Everything — payments, fittings, staff assignments, measurements, notifications — orbits the job order. When a shop owner opens an order and sees the full timeline (created → DP paid → cutting → sewing → QC → fitting → balance paid → picked up) with timestamps and staff names — that's an ERP. When they see a status dropdown — that's a student project.
>
> The third transformation: **the system enforces business rules.** No production without deposit. No completion without balance. No fitting appointment without a linked order. No branch manager seeing another branch's data. When the system says "no" — that's an ERP. When the system lets you do anything — that's a student project.
