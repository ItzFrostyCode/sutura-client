## Update 2026-10-21 — consultation first, order rules, people, release, batches

Details and endpoints: [`STATUS.md`](STATUS.md) ("Consultation first, order rules, batches"). Code beats this note.

- **Before the order:** a consultation starts only once the shop knows who it is (a customer the shop has, or a new name + mobile number; a number the shop already knows reuses that customer). The walk-in account's placeholder `walkin_…` email is never shown. What was said (`visit_notes`), how many people and where the design comes from (`design_source`: shop's · customer's finished · customer's to redo · none) are copied onto the order as "Consultation notes" and shown on the order and the work ticket.
- **Gates are unchanged in order:** specs approved → measurements verified → price final → customer accepts → deposit → authorize → production. Measuring after the design is approved needs no new lock. Service rules (measurements, fitting, payment, minimum quantity) are the order's **starting values**; the owner / branch manager can change them for one order with a reason (`order_rules_changed`). The minimum quantity only warns.
- **Handover and completion:** a group order counts **garments**: each person's own pieces (`qty` on the team list, one when none) added up (`JobOrder::garmentCount()`, 2026-10-28), not `quantity` (which stays 1) and not just the number of people (`people_count`). Older orders without `people_count` keep counting `quantity`. A handover needs the balance paid unless the owner / branch manager **releases with a balance due**; the order then stays in Balance Payment & Handover and **Completed needs the balance at 0**.
- **Batches:** a group order can be split before production into linked orders (one per payer). Each part has its own total, deposit, due date, handover and tracking code; the overall figures are worked out from the parts.

## Update 2026-10-16 — simple sequence (pre-production steps, five plain stages)

Spec: `SUTURA/chatgpt Reply to  your executive summary.md`. Code beats this note.

- **A request has six saved steps** (`App\Support\OrderPreProduction`, shown on the order's Steps tab): request accepted · details & sizes (specs, measurements, the customer's own items, pieces/people/sizes edited inline) · price sent · customer answer · deposit · order confirmed (**Confirm order** appears only when 1–5 are done). Nothing extra is stored; coming back lands on the first unfinished step. Once confirmed, the Steps tab shows **Getting ready** instead: materials ready, tailor assigned, **Start production** (first task `pattern_making`, `mass_cutting_printing` for a bulk order, `in_repair` for a repair — never `design`; the server refuses any other first move).
- **Online request without an appointment:** `POST /stores/{slug}/order-requests` (client `/store/{slug}/request`). It waits as `pending` until the owner/manager accepts it (`POST …/jobs/{job}/accept-request`); nothing is paid or started.
- **Quotation versions:** every save of the quotation adds a row in `order_quotation_versions` (who, why, total, terms). A change after the price was sent needs a reason. The proposed **payment terms** (deposit %, full, or pay on pick-up) and a **valid-until** date travel with the price; the customer sees them before answering and they lock when the customer agrees. Changing price, date or terms after that voids the answer.
- **Customer decision:** `POST /my-orders/{id}/decision` with `accept | changes | decline`. Decline closes the order as `cancelled` with reason `quotation_declined` (only if nothing was paid). The customer cannot send payment proof before accepting.
- **Authorization:** confirming records `production_authorized_at/by`; production cannot start without it. Only the owner or a branch manager can confirm or cancel an order on the flow, and a completed / cancelled / rejected flow order can no longer change status.
- **Tailor changes** are kept in `job_order_assignee_events` (from, to, reason, by); a reason is required once work has started.
- **Customer view:** one server-built `progress` (`App\Support\OrderProgress`): Request · Confirmed · Being made · Ready · Done, plus one plain sentence and the next action. Same for signed-in customers and guests (`/track/{code}`, no action shown). Fitting, adjustments and the internal tasks are notes inside a stage, never extra stages; the bar never moves backwards.
- **Shop view:** Orders page = the same five stages, oldest order on top with its place in line and received date; a one-tap "Next" for the cutting/sewing tasks. Order page = three tabs: Steps, Details, Payments.
- **Texts and notices:** new in-app/email notices for request accepted, price ready, price changed (`OrderUpdateNotification`); the optional text "price is ready" is off by default; the "ready" text now says what to bring (balance, full payment, or nothing). Texts still go through the shop's outbox, so the shop reviews and sends.
- **Not done / open:** see section 7 of the spec (who accepts online requests beyond owner/manager, quote expiry reminders, legacy order mapping, receipt numbers). Internal statuses were not changed.

## Update 2026-10-16 — Create Job Order form simplified

`/dashboard/jobs/new` (`components/jobs/JobCreateForm.tsx` + `form/*`) was five plain steps (**Customer → What is being made → Details → Who works on it → Price and date**); since 2026-10-28 it is four, see the last section. Code beats this note.

- **Same lists the customer searches by:** one garment search box (`form/GarmentStep.tsx`) built from `lib/garmentTaxonomy` plus any name typed on a shop's designs, the shop's own garments first; then only the services that work on it (`garment_types`; empty = any garment only for Alterations / Customization). A design (optional) fills in its service, price, days and photo and is filtered by the same garment.
- **Derived, not asked:** repair flow (condition notes) from an alteration service, team list from a bulk service, measurements hidden when the service says none are needed. The old three-way "From a Design / Made to Order / Alteration" switch is gone.
- **Staff step** (owner / branch manager): staff whose Skills (Staff page) mention the garment, its category or the service are listed first as "Skilled in …".
- **Price and date are suggestions** (service or design price × quantity, service turnaround) until typed over; total = price + rush fee − discount. An empty price saves a zero-total order to be quoted in Order Steps (it now starts `unpaid`, not `paid`).
- **Saved on the order:** `custom_order_data.garment_type` (readable name), `.garment` (slug), `.garment_group`; the old `garment_category` is still filled where a match exists (barong, gown, suit, filipiniana, uniform, alteration_repair) so the work ticket and reports keep working.

**Orders board (2026-10-16):** the five stages are tinted full-height lanes with a count pill; a summary strip (active, waiting on you, due in 2 days, overdue, balance to collect — owner/manager only) is worked out from the loaded orders and hidden when there are none; the Request lane lists real appointments that took place but have no order yet ("Ready to write up"), each opening Create Job Order pre-filled (`board/WaitingAppointments.tsx`).

- **Scope audit:** per-order materials (supplier, cost, "to buy", supplier recovery) were built first, then **removed** — they break the thesis Limitations (no inventory, material stock, purchase orders or supplier/procurement processes). Materials are now a **ready / waiting** yes/no with a note, plus an assessment of the customer's own fabric. See `PRD.md` difference 5.

- Side fix: `job_orders.material_source` defaulted to the invalid `shop_supplied`; the default and old rows are now `store_supplied`.

## The sequence (Kanban columns, left to right)

| Band | Status key | Label |
| --- | --- | --- |
| Set up | `pending` · `confirmed` · `awaiting_materials` | Pending · Confirmed · Awaiting Materials |
| In production | `design` · `pattern_making` / `mass_cutting_printing` · `cutting` · `sewing` | the shop's internal tasks (the customer just sees "In Production") |
| Quality check | `qc_ironing` | Quality Check |
| Fitting & collection | `ready_for_pickup` · `ready_for_fitting` · `final_adjustments` | Ready for Final Fitting / Collection · Customer Fitting / Inspection · Adjustment / Correction |
| Handover | `balance_handover` · `completed` | Balance Payment & Handover · Completed |

Paths: A) production → QC → ready → handover → completed. B) …→ ready → **fitting** → handover. C) QC or fitting fails → **correction** → back to QC → ready → fitting again if needed → handover. Fitting is skipped when the order's fitting requirement is `none`.

## Gates (single source: `app/Support/OrderReadiness.php`)

| To do this | The server requires |
| --- | --- |
| Make the quotation **final** | price, completion date, specs approved, measurements verified (unless not needed), the customer's own fabric assessed *suitable* (when they bring it) |
| **Confirm** | final quotation, specs approved, customer approval, deposit **verified** |
| **Start production** (`confirmed` → first task only: `JobOrder::firstProductionTask()`) | materials marked ready, measurements verified, a tailor planned, production authorized, **deposit still met** (a change approved after confirming can raise the total) |
| → **Ready for Final Fitting / Collection** | quality check recorded as passed, no open correction |
| → **Customer Fitting / Inspection** | QC passed, fitting needed (not `none`), coming from Ready |
| → **Adjustment / Correction** | at least one open correction (a QC defect, a fitting issue, or a customer change) |
| Adjustment → **Quality Check** | every correction done |
| → **Balance Payment & Handover** | QC passed, no open correction, and if a fitting is *required* it was passed |
| Record a **handover** | status is Balance Payment & Handover **and the balance is paid** |
| → **Completed** | every garment handed over, no open correction, balance 0 |

Moving back to production, QC or correction starts a new round, so QC and the fitting have to be passed again. A saved quotation that changes the total or date clears an earlier approval. A customer **change request** is quoted and approved first; approving adds its price to the total and balance, and a new completion date is written to the audit log with the reason. After production has started, a higher total does not re-lock the deposit gate.

## Customer view and notices

The customer sees one status: Pending → Confirmed → In Production → Quality Check → Ready for Fitting / Collection → (Fitting / Inspection) → Payment & Handover → Completed, with *Adjustment / Correction* shown only while something is being corrected. They are emailed when work starts and when the order is **Ready** (quality check passed; fitting or collection; balance; settle and take home in one visit), not for each internal task, the fitting or the handover. Internal tasks, assignments and notes stay shop-only.

## Cancellation refund

Suggested = paid − "spent, cannot recover" (an amount the owner types, with a note). Changing the suggestion needs a reason. It is **recorded only** — SUTURA never moves money — and does not change revenue figures yet.

## Update 2026-10-28 — New Job Order in four steps; people, pieces and measurements

`/dashboard/jobs/new` is Bongo's approved four-step flow, built from the same sections as before (`JobCreateForm.tsx` + `form/wizard/*`): **Customer → Order details → Sizing → Review & pay.** One step on screen, one main button (Next, then Create Job Order), Back always available. Bongo's own order is Customer → Measurements → Specifications → Invoice; the service is chosen *before* sizing here because whether measurements are needed, and which size chart applies, come from the service. Code beats this note.

- **People, pieces, measurements are three different things.** A *wearer* is a person (a row of the team list, `people_count`); a *piece* is a garment (`qty` per wearer; one person can need several); a *measurement profile* belongs to a person and a garment and never decides the number of pieces. One wearer = the Order details "How many pieces?" field plus one profile; two or more wearers = the Sizing step's team list (Name · Size · Pieces; Custom Fit opens a measuring panel). The minimum quantity, handover, completion gate and the default price share when splitting an order all count **pieces** (`JobOrder::rosterPieces()` / `garmentCount()`); the client's `jobPieces()` / `jobPeople()` agree.
- **Sizing only asks what the order needs.** The measurement need is resolved design → service → shop default (`form/measurementNeed.ts`, same order as `OrderRequirements`). *Not required* shows one line and "Add measurements anyway"; nothing is linked or recorded unless asked. Otherwise one of: saved profile · take measurements now (Custom Fit) · standard size · measure later. **Measure later** is allowed and keeps the order unmeasured: it cannot be verified or started until measurements or sizes exist (`OrderReadiness::measurementsRecorded`, `verifyMeasurements`); payment alone never makes it ready.
- **Profiles:** a new profile is named for the garment ("Polo Shirt Profile") unless named; recording under a name the customer already has makes its **next version** (history kept) instead of a duplicate; another name is another profile. An individual order measures **one** wearer (the old "Person 1 / Person 2 / Add person" bar is gone from it). An online order may name the wearer (`wearer_name`) so a child's profile never replaces the parent's.
- **Dates:** one turnaround drives the suggested due date, "Ready around" and the "too quick" warning: the design's own estimate, else the service's; the suggested due date is the **end** of a range, counted in calendar days from today.
- **Review step** lists every job order that will be created (an extra service is its own order, with its own price), the pieces, what is still open, and when it should be ready.
- **Each Custom Fit wearer has their own profile (2026-10-28).** On a team order, the points typed under a Custom Fit row are saved by the server in the same request as the order (`JobMeasurementSync::syncRoster`) as that customer's profile **"{Name} — {Garment} Profile"**, versioned when that exact name exists, and the row keeps the profile's id (`measurement_id`). A row can instead use a saved profile of the same customer; a profile of another customer is refused (422). They show in the Client Book and Measurements & Specs like any profile. **Custom Fit counts as measured only with a profile or typed points** (`OrderReadiness::measurementsRecorded`); the size label alone no longer does.
- **Steps tab (2026-10-28).** In the request stage only the step you are on has buttons (marked "Do this now"); other steps say Done or Later, so there is one thing to do at a time. The Quotation card keeps the price, terms, versions and Edit; whether the customer answered and the deposit came in is told once, by the steps. Tailors, Client and the customer-status card sit in a folded "About this order". Making and handover were already one main button at a time and are unchanged.
- **Three decisions on measurements and the team list (2026-10-29).** Chosen with the owner so they are not re-opened:
  - **Measurement is not made universally required.** The per-service setting stays (design → service → shop default); the server rule is unchanged. What changed is the *display*: "What this order needs" no longer says "Measurements: Not required" when sizing was taken. It has a **Sizing** row that says what was actually recorded: one person → "Standard size M · no body measurements" or "Body measurements · {profile}"; a team → "8 of 10 people sized · 1 of 2 Custom Fit measured". Standard size = sizing recorded; **Custom Fit** needs real measurements before it can be verified; **Measure later** stays incomplete when measurements are needed; a measurement-free service is never forced to record any (`JobRequirementsCard`, `OrderReadiness::measurementsRecorded`).
  - **Team list on a phone is cards, on a larger screen a table.** Each person is a card with name, size, pieces, the other columns and Custom Fit (New Job Order step 3 and the order's Details tab), so there is no sideways scroll on a 640px table.
  - **One team section in Details, not two.** The order's Details tab has a single **Team list** (person, size — "Custom · measured" or "to measure" — pieces, done mark) with **Edit team list** (until production starts). The old duplicate Specifications/Team Roster tables and the one-wearer measurement card are gone for team orders; garment specifications that are not part of the wearer list stay. Saving the spec table sends whole rows back, so `qty` and the measurement-profile link are no longer lost and a single order never turns into a nameless team.
  - **Server rule that goes with it:** editing the team list moves `people_count` to the length of the list, but the number of people or pieces can only change while the order is still a request (`pending`); after confirmation it is refused with 422 (names, sizes and remarks can still be corrected). `UpdateJobOrderRequest` now accepts the same per-wearer fields as the create request (`qty`, `measurement_id`, `fit_metrics`, `roster_unit`) and a linked profile must belong to the order's customer. Tests: `WearerQuantityTest` (group F).
- **Team list redesign (2026-10-29, New Job Order step 3).** One row per person. **Wearers and garments are different numbers** (two people with two polos each = 2 wearers, 4 garments): the review, price share, minimum, handover and tickets count the garments, the people count counts the rows. So a person stays one row and **Pieces** is an optional column (add it with the **+**; typing Pieces, Qty or Garments makes the `qty` column; 1 when absent). **Top & Bottom coverage does not change any count by itself.** What one ordered unit is comes from the **pricing option** of the service (next note), never from the sizing choice. Default columns: **Person Name** (required), **Nickname** (`print_name`), **Jersey Number** (`number`), **Role / Position** (`position`) — those three optional — and **Size** (required); a service's own per-person fields are added after them. The **+** at the top right of the header adds a column beside the last one (on a phone it sits next to the team name); **Add person** / **+ 5 people** under the rows add rows. Cards below 768px, table from 768px up. A **Custom Fit** row asks *what is measured*: **Top**, **Bottom** or **Top & Bottom** (Top/Bottom sections, each with its own "add a measuring point"); changing it clears the points of the part no longer measured. The choice is sent as `measure_area` (validated `top|bottom|both` on create and update) and kept on the person's profile as `_area` (no choice = `both`, as before). Step 3 runs full width with the same side margin as the header and footer (`px-4 sm:px-6`) at every size; steps 1, 2 and 4 keep the centred 3xl column.
- **Cancel "Made by mistake" (2026-10-29):** the cancel panel now says up front, and disables Cancel, when money was already taken (the server refuses it, `OrderCancelController`); the refund line is not shown for a mistake.
- **A request asks for no payment (2026-10-29).** The customer's online order form (`POST /stores/{slug}/service-orders`, 4-step form, step 4 "Invoice & Payment") no longer needs a GCash account or a receipt to be placed, and the server records no payment with it. The order lands `pending`/`unpaid` and follows the normal sequence: the shop reviews and accepts it, confirms details and price, the customer accepts the price, and **only then** is the deposit due — paid from My Orders (`POST /my-orders/{id}/payments`) and verified by the shop. What the customer picks at the request (Downpayment or Full) is kept as a *preference* (`custom_order_data.payment_term`), the shop confirms the real terms with the price; a trusted customer still owes nothing up front. The old receipt/GCash fields are ignored if an older client still sends them. Removed: `OrderGcashPayment` and the receipt upload in `useServiceOrder`.
- **Money figures are never cut to "…" (2026-10-29):** the customer profile's Payments tab shows Billed / Paid / Balance due as tiles (stacked on a phone, three across from 640px, amount wraps), and Payments → Job Balances is cards up to 1023px, table from 1024px.
- **Measurement forms are one pattern (2026-10-29).** "What needs to be measured" is **one row** of three buttons — Top · Bottom · Top & Bottom (`shared/Segmented`, used by `AreaSelector`) — and every part's fields are **one column**, Top and Bottom stacked (no two-column grids, no side-by-side parts). The same on the order's *Record or Link Measurements* window (now built on the shared `Modal`, full screen on a phone, same field/label/button sizes and the same saved-profile list as New Job Order), the single-person form in step 3, and a Custom Fit person on the team list. The default on the *order's* measurement window is Top & Bottom; in New Job Order nothing is pre-selected (see the next note), and the server falls back to `_area` = `both` when no area was sent. The window is titled "Record or Link Measurements" (or "Edit Garment Measurements" once one is linked), matching its button.
- **"Covers first" — one sizing rule for one person, a pair or a team (2026-10-29).** In New Job Order step 3 the first question is always **what the person gets: Top, Bottom or Top & Bottom**, before any size; nothing is pre-selected and Next is blocked until it is chosen. Everything after follows it:
  - **Standard size:** one size per covered part — *Top size* and/or *Bottom size* (solo: two chip rows for top & bottom; team: two selects in the Size cell). The size chart's numbers shown under a size are only that part's columns (chest/shoulder for a top, waist/hips for a bottom; `isBottomPoint`).
  - **Custom Fit / measuring:** only the part that is Custom Fit shows its measuring points (a top & bottom person with only the bottom Custom gets only the bottom points). No Top/Bottom choice inside the measuring panel any more: it was already made.
  - **Saved profile:** shown as before; if its area (`_area`) does not cover what the person gets, a plain amber note says so (not blocked).
  - **Team:** one **Everyone gets** choice above the list sets every row at once (confirms before clearing sizes that no longer fit); a **Covers** column (required, before Size) overrides one person. New people start with what the list already agrees on. Changing a person's Covers after they had one clears their sizes and points, because a size then means a different part.
  - **Stored:** each team row has `measure_area` (`top|bottom|both`), `size` (the top's, or the only size) and `bottom_size` (top & bottom only); a solo order has `custom_order_data.measure_area` and `standard_size` ("M", or "M / L"). The order's spec table gets a Covers drop-down and a Bottom size column, so editing the list later cannot put free text in Covers.
  - **Server:** `OrderReadiness::measurementsRecorded` needs `bottom_size` for a `both` person, and Custom Fit on either part needs measurements or a saved profile. Orders made before this have no `measure_area` and behave as before (one size).
  - **Not covered:** the Details tab's "Edit team list" is the spec table (Covers is a drop-down there, sizes are text). Free-form quote requests (`order-requests`) only carry a measurements note: the shop sizes the order when it writes it up. The `bulk-orders` and `made-to-order` endpoints have no screen calling them.
- **Sizing is one if / else, shop and customer alike (2026-10-29).** Payment never depends on it: a service has a price and payment rules whatever its sizing, and a fully paid order with the sizing still open is still not ready for production.
  1. **The service needs no body measurements** (`measurement_requirement = none`: button or zipper replacement, patching, seam repair…) → nothing about sizing is asked, and anything sent anyway is dropped (server and form). Only the details the work needs (repair condition, photos) remain. Set it per service from the actual work, not for a whole group such as Alterations & Repairs.
  2. **A fit change on a repair** (hemming, shortening, taking in) → no body measurements either, only **"Where and how much to change"** (optional note `custom_order_data.local_adjustment`) on the customer's repair request and on the shop's repair details.
  3. **Otherwise sizing applies, and what the person gets comes first:** Top / Bottom / Top & Bottom. The customer's online order form (step 2, now called **Sizing**) asks it before anything else, for one person and for a batch; the server refuses an order that needs sizing without it (422).
  4. **Then how the sizes are known** — one person: **saved profile** (with a plain note when its `_area` does not cover the choice) · **standard size** (a size per covered part, moved here from step 3; the shop's chart numbers for that part under the chips) · **own measurements** (only the covered part's fields, one per row; the server keeps only those points) · **the shop measures** (Measure later: the order can be accepted and paid, but is not "sized"). A batch: a count per size, and for Top & Bottom a second count per bottom size that must add up to the same number of sets (422 otherwise; quantity = sets).
  5. **Stored:** `measure_area`, `standard_size` ("M" or "M / L"), `size_breakdown` (+ `size_breakdown_bottom`), and a typed profile now carries `_area` **and `_unit`** (a centimetre profile used to be saved without its unit and read as inches). Shown on the order: standard size, bottom size counts ("sets"), and the Top/Bottom badge.
  **`none` is not "no information":** the service's own questions (required ones still enforced), the fabric, photos and notes are still taken, and the order still needs its design/details approved (`specs` blocker) before it can be confirmed; only the body measurements (and their `measurements` blocker) are skipped.
  Tests: `CustomerServiceOrderTest` (24): area first, none → no sizing but details kept, both sizes, only the covered points, bulk sets, repair note.
- **Pricing options say what they cover and what one unit is (2026-10-29, code ready, migration NOT run).** Each `service_pricing` option has two separate, optional settings: **`covers`** (`top` | `bottom` | `both`: decides the sizing asked) and **`sold_as`** (`garment` | `set`: what ONE ordered unit is; a set is one top and one bottom, so two physical garments). Null = not configured: every existing option and order behaves exactly as before (no coverage implied, one unit = one garment). The API refuses only one combination: a set that does not cover top & bottom. A garment may cover both (one garment that is a top and a bottom).
  - **Five numbers, kept apart:** wearers (`peopleCount()`, rows) · per-wearer `qty` (units that person asked for) · **ordered quantity** (`orderedQuantity()`: the units, in the option's unit) · **price** (the option's amount × ordered quantity, never multiplied by garments) · **physical garments** (`garmentCount()` = ordered quantity × garments per unit, 2 for a set). The minimum (`min_order_qty`), the price share of a split and the tracker's "quantity" use the ordered quantity; only handover, its completion gate and the "people / garments" wording use the garments. Example: 2 people × 2 sets each = 2 wearers · 4 ordered sets · 8 garments to hand over.
  - **Snapshot on the server:** when an order is made (customer `service-orders`, shop `jobs` with `pricing_id`) the server copies the option's label, coverage and unit into `custom_order_data` (`option`, `option_covers`, `option_sold_as`); anything the client sends under those keys is discarded, and an edit of the order cannot change them. Editing or deleting the option later never changes an old order. An option that covers something also fixes the coverage of the one wearer and of every person on a team list.
  - **Customer online order:** the option is the first thing in **Sizing** (it decides the coverage, so the Top/Bottom choice is replaced by a line when it covers something) and is no longer in step 3; prices read "₱600 per set"; the quantity is in sets and the summary shows "Garments to hand over".
  - **Shop New Job Order (Order details):** an **Option** list appears after the service; it is required once any option of that service is configured (otherwise it only suggests the price); the unit price follows the option; Covers is locked on the Sizing step; the review shows sets and garments. Header chips, the quotation step and the Ready-column handover count read "N sets · G garments".
  - **Service editor (Prices & add-ons):** each row has **Covers** and **One ordered unit is**.
  - **Migration:** one migration, `2026_10_29_120000_add_covers_and_sold_as_to_service_pricing`, adds two nullable columns (no default, no backfill); not run on any real database. Until it is run the code keeps working (the options are read whole, and saving a service skips the two fields), but nothing can be configured. The leader runs it.
  - **Not covered:** only a top + bottom set (a three-piece suit would need a real set-composition model); existing services that really are set-based must be configured by their shop; the legacy `bulk-orders` / `made-to-order` endpoints and the customer's catalog flows do not read it. Tests: `PricingOptionUnitTest` (9).
- **One vocabulary, form and detail alike (2026-10-29).** `src/lib/orderUnits.ts` holds every word for what an option covers and what one unit is; the service editor (CRUD), both option lists, the Sizing step, the order's Details, chips, review and the service page all read it. **Covers**: Top · Bottom · Top & Bottom. **Sold as**: Garment · Set (top + bottom). Not configured: **Not set**. The service's line is an **Option**; sizing is **Sizing**. Ordered quantity is in **pieces** or **sets**; **garments** is only what is handed over. The order carries its own counts from the server (`ordered_quantity`, `garment_count`, `sold_as`), and screens read them instead of recomputing; only an order not saved yet (the review in New Job Order) is worked out on the client. The browser check, scenario by scenario, is in `QA-ORDERING.md`.
